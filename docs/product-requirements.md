# TechScout（技术侦察台）产品需求文档

> 文档状态：需求基线 v1.1  
> 项目性质：个人独立学习项目 / 作品演示  
> 目标周期：8–10 周 MVP  
> 默认语言：简体中文  
> 更新日期：2026-09-01

## 1. 文档目的

本文档定义 TechScout 的产品目标、MVP 范围、数据策略、Agent 工作流、技术边界、验收标准和学习路线，用于指导后续架构设计与实现。

TechScout 借鉴技术情报类产品的通用业务流程，但采用 clean-room 方式独立设计和实现。当前公司项目仓库仅用于理解通用业务场景，不直接复制其源码、品牌、文案、私有接口、私有数据、提示词、评分算法或未知的后端实现。

本文档不是当前 TechAlpha 前端的改造方案，也不承诺替换任何公司内部或生产系统。

## 2. 背景与问题

硬科技研究往往需要同时处理技术分类、专利、公司主体、论文、新闻和公开活动等异构信息。传统人工流程存在以下问题：

- 研究问题难以快速拆解为稳定、可复用的检索策略。
- 专利申请人、公司别名、母子公司和历史名称难以统一。
- 数据来源分散，人工收集和去重成本高。
- 研究结论容易脱离原始证据，无法追溯或复核。
- 一次性报告难以复现，换模型、换数据后缺少回归评测。
- 公开 API 受限流、许可、覆盖区域和稳定性影响，实时演示容易失败。

TechScout 通过可控的多 Agent 工作流，将“研究规划—多源采集—实体消歧—证据核验—公司发现—报告生成”串成一个可观察、可恢复、可评测的研究过程。

## 3. 产品定位

### 3.1 一句话定义

TechScout 是一个面向产业研究员和技术投资研究者的 AI 技术情报平台：用户输入技术方向，系统利用专利、论文、公司与新闻公开数据发现候选企业，并生成带证据引用的结构化研究报告。

### 3.2 目标用户

MVP 主要服务以下用户：

- 希望学习 Agent 工程、数据采集和 RAG 的开发者本人。
- 需要演示完整 AI 工程能力的面试官、同事或技术评审者。
- 以技术路线和企业线索为关注点的产业研究员或技术投资研究者。

MVP 按单用户设计，不建设团队、多租户和复杂权限系统。

### 3.3 产品边界

TechScout 是技术情报和研究辅助工具，不提供买入、卖出、估值或其他投资建议。所有模型生成内容均需区分来源事实与模型推断。

## 4. 项目目标与非目标

### 4.1 MVP 目标

1. 跑通从技术问题到候选企业和研究报告的完整纵向链路。
2. 使用真实公开数据源，同时支持稳定的离线演示与回归测试。
3. 实现可控、可恢复的多 Agent 工作流，而非不可预测的自由 Agent 群聊。
4. 为关键事实提供来源、引用片段、采集时间和可信度。
5. 展示 Agent 的工具调用、阶段状态、成本、耗时和失败信息。
6. 建立固定评测集，使提示词、模型或工作流调整可以量化回归。
7. 覆盖 TypeScript 全栈、Python Agent、爬虫、数据工程和可观测性等学习目标。

### 4.2 MVP 非目标

- 不建设全球全量公司、专利、论文或新闻数据库。
- 不承诺完整覆盖中国工商、融资、招投标或专利法律数据。
- 不绕过登录、验证码、付费墙、robots 或其他技术保护。
- 不提供精确但缺乏依据的“投资潜力 87 分”等综合评分。
- 不实现多租户、团队协作、套餐、计费和复杂权限。
- 不实现生产级高可用、跨区域容灾和大规模分布式爬取。
- 不在 MVP 中实现定时跟踪预警。
- 不同时引入多个 Agent 框架进行横向比较。
- 不直接展示模型私有思维链。

## 5. 成功标准

当用户输入一个技术方向后，系统能够：

1. 生成 1–3 个可编辑的技术子方向和检索策略。
2. 在用户确认后调用真实或离线数据工具执行研究。
3. 从专利受让人、论文机构、新闻实体和用户资料中发现候选企业。
4. 对公司别名、外部 ID 和专利权人进行实体消歧。
5. 为最多 10 家候选企业给出可解释的排序和匹配理由。
6. 生成包含专利、论文、新闻、风险和信息缺口的中文报告。
7. 对报告关键事实提供可展开的证据引用。
8. 在刷新页面或部分数据源失败后恢复任务，并支持重试或取消。
9. 在 Fixture 或 Replay 模式下稳定复现完整演示。

## 6. 核心概念

| 概念 | 定义 |
| --- | --- |
| 研究项目 | 用户围绕一个技术问题发起的一次持续研究容器 |
| 研究运行 | 研究项目下的一次具体 Agent 执行，绑定模型、提示词和数据版本 |
| 技术方向 | Agent 从原始问题拆解出的可检索子主题 |
| 检索策略 | 关键词、CPC 分类、排除条件、时间和区域等组合 |
| 候选企业 | 从专利、论文、新闻或用户清单发现的待核验主体 |
| 规范实体 | 经过别名合并并关联外部 ID 的公司、机构或个人 |
| 事实声明 | 从来源中抽取的结构化主张，包含证据和有效时间 |
| 证据 | 支持事实或推断的原始来源、片段、URL 与采集记录 |
| 垂直领域公司—专利数据库 | 持续积累特定 AI 领域的公司、专利、主体关系和来源历史，是产品核心数据资产 |
| 种子数据集 | 垂直领域数据库的首个可版本化数据包，用于初始化、复现和扩充主库 |
| Fixture 模式 | 使用仓库内极小固定样本执行测试和演示 |
| Replay 模式 | 重放已记录的工具返回和 Agent 事件，不访问外部服务 |
| Live 模式 | 实时访问已配置的数据源，并增量保存研究工作集 |

## 7. 核心用户流程

```text
创建研究项目
  ↓
输入技术方向或研究问题
  ↓
Planner 生成技术子方向、CPC 与关键词检索策略
  ↓
用户编辑并确认研究计划
  ↓
并行检索专利、论文、公司和新闻
  ↓
提取专利受让人、论文机构和新闻实体
  ↓
公司实体消歧与人工确认
  ↓
Evidence Agent 去重、冲突检测、可信度标注
  ↓
生成候选企业长名单及可解释排序
  ↓
用户选择企业并补充调查
  ↓
Report Agent 生成带引用报告
  ↓
用户追问、修订并导出 Markdown
```

## 8. 功能需求

### 8.1 研究项目与任务

#### FR-001 创建研究项目

用户可以输入自然语言研究问题创建项目，例如“寻找适用于工业视觉质检的边缘 AI 推理芯片公司”。

验收要求：

- 输入不能为空，并设置合理的长度限制。
- 创建后立即生成唯一项目 ID 和初始研究运行。
- 项目保存标题、原始问题、创建时间、更新时间和状态。
- 用户可以重命名、归档或删除项目。

#### FR-002 项目状态恢复

- 刷新页面后恢复到最后查看的研究阶段。
- 每个长任务保存检查点和最近事件序号。
- 用户可以取消正在执行的运行。
- 失败节点可单独重试，不重复覆盖已经成功的数据。
- 同一幂等键不得创建重复的采集或报告任务。

### 8.2 研究规划

#### FR-010 自动拆解技术方向

Planner Agent 将原始问题拆成 1–3 个技术子方向，每个方向包括：

- 名称和范围说明。
- 包含关键词和排除关键词。
- 建议 CPC 分类及解释。
- 时间、区域和数据源范围。
- 潜在歧义与漏检风险。

#### FR-011 人工确认计划

- 用户可增删、编辑和排序技术方向。
- 用户可修改关键词、CPC、排除条件和数据预算。
- 正式采集前必须确认研究计划。
- 重新生成计划时保留历史轮次，便于比较。

### 8.3 多源数据采集

#### FR-020 数据源适配器

所有外部来源通过统一适配器接入，至少实现：

- `search`：根据领域查询返回轻量候选。
- `fetch`：按外部 ID 获取详情。
- `normalize`：转换为内部标准结构。
- `health`：检查认证、配额和可用性。
- `provenance`：返回来源、许可、采集时间和版本信息。

数据源失败必须软降级，不得由模型补写不存在的事实。

#### FR-021 专利采集

MVP 支持：

- 按关键词、CPC、申请人和时间范围检索。
- 获取出版号、申请号、标题、摘要、优先权日、申请日、申请人、发明人、CPC、专利族和可用法律状态。
- 根据研究方向计算相关性，并保留计算理由。
- 对同一专利族进行归并，避免重复计数。
- 保存原始响应、规范化记录和来源时间。
- 对字段缺失或不同国家覆盖差异进行明确标注。

#### FR-022 公司与机构数据采集

MVP 支持通过公司名称、别名和外部 ID 查询：

- 规范名称、司法辖区、注册地址和官网。
- LEI、CIK、Companies House number、ROR/OpenAlex ID 等外部标识。
- 可用的曾用名、证券代码和母子关系。
- 来源更新时间和覆盖限制。

公司数据缺失时允许继续分析，但必须标记为未核验主体。

#### FR-023 新闻与网页采集

- 使用 GDELT、RSS 和选定公开网页发现新闻与事件。
- 保存标题、来源、发布时间、URL、实体匹配和事件分类。
- 默认不批量保存新闻全文，仅保存必要引用片段和抽取事实。
- 采集网页前检查 robots、站点条款和速率限制。
- 不绕过登录、验证码、付费墙或技术保护。

#### FR-024 论文与科研活动

- 使用 OpenAlex 和 ROR 查询技术主题、论文及机构。
- 将企业研究机构与规范公司实体进行关联。
- 保留论文 DOI、标题、日期、主题、作者机构和引用信息。
- 论文信号作为科研活跃度证据，不等同于工商或商业能力证明。

### 8.4 用户资料导入

#### FR-030 上传资料

用户可以补充：

- PDF：论文、专利、公司报告。
- CSV：公司或专利种子清单。
- URL：公开网页。

要求：

- 设置单文件大小、单次数量和文件类型限制。
- 对文件进行 hash 去重和恶意内容基础检查。
- 所有上传来源标记为“用户提供”。
- 解析失败不影响其他研究流程。
- 用户可删除文件及其派生分块和向量。

### 8.5 实体消歧

#### FR-040 公司实体匹配

Entity Resolution 节点综合以下特征：

- 规范化名称和别名相似度。
- 注册号、LEI、CIK、ROR 等强标识。
- 官网域名、地址和司法辖区。
- 专利受让人、论文机构和新闻中的上下文。
- 母公司、子公司、历史名称和并购关系。

匹配结果分为：

- 已自动确认：强标识一致且无冲突。
- 待人工确认：中等置信度或存在多个候选。
- 暂不合并：证据不足或冲突明显。

系统必须记录匹配特征、置信度、确认者和确认时间，禁止仅凭 LLM 自由文本合并实体。

### 8.6 候选企业发现与排序

#### FR-050 多渠道发现

候选企业来自以下集合的并集：

- 专利申请人和受让人。
- OpenAlex/ROR 企业研究机构。
- 新闻、官网和公开活动中的企业实体。
- 用户上传的公司清单。

每家企业显示发现渠道，不宣称候选名单覆盖全部市场。

#### FR-051 可解释排序

MVP 不生成伪精确的综合投资分。排序指标至少包括：

- 与技术方向的语义及规则匹配程度。
- 相关专利数量、时间趋势和专利族分布。
- 专利法律状态和重点专利证据。
- 论文、产品和新闻的交叉证据。
- 信息完整度、新鲜度和来源可信度。
- 冲突、缺失与实体匹配风险。

用户能够展开查看排序理由和底层证据。

#### FR-052 企业长名单

- 默认最多保留 10 家候选企业。
- 支持按技术方向、发现来源、区域和证据完整度筛选。
- 支持关注企业并进入公司详情。
- 支持排除误报，并将用户反馈保存到评测数据中。

### 8.7 公司详情与研究报告

#### FR-060 公司详情

公司详情至少包含：

- 规范身份和别名。
- 与研究方向的匹配摘要。
- 相关专利、专利族和时间趋势。
- 论文与科研活动。
- 新闻及公开事件时间线。
- 数据来源、冲突、缺失项和更新时间。

#### FR-061 报告生成

报告采用固定主结构：

1. 研究问题与范围。
2. 技术方向与检索策略。
3. 候选企业长名单。
4. 企业与技术匹配证据。
5. 专利布局、趋势和重点专利。
6. 新闻、论文及公开活动时间线。
7. 风险、来源冲突和信息缺口。
8. 综合结论与后续调查建议。
9. 完整来源列表和执行记录。

#### FR-062 引用与推断标记

- 关键事实必须关联至少一个来源片段。
- 每条引用显示来源、URL、采集时间和原文。
- 模型归纳或推断必须明确标记，不能伪装为来源原文。
- 来源冲突时同时呈现不同说法，不静默选择一方。
- 用户可以从报告跳转到证据详情或原始页面。

#### FR-063 报告交互与导出

- 支持展开或折叠章节。
- 支持围绕已有证据追问。
- 支持人工修订报告正文。
- 保存自动生成版本和人工修订版本。
- MVP 支持 Markdown 导出，PDF 导出进入第二阶段。

### 8.8 执行轨迹与可观测性

#### FR-070 用户可见轨迹

前端展示：

- 当前工作阶段和整体进度。
- Agent 和工具名称。
- 使用的检索式、CPC 和数据源。
- 找到、过滤和采用的证据数量。
- 结构化判断理由摘要。
- 重试、降级、取消和人工确认记录。

不展示模型私有思维链。

#### FR-071 工程观测

每次 Agent 运行记录：

- 模型供应商、模型名和参数。
- 提示词和工作流版本。
- 输入输出 token、费用与耗时。
- 工具调用输入输出摘要和错误。
- 状态转换、重试次数和检查点。
- 数据集版本与引用来源。

### 8.9 Live、Fixture 与 Replay

#### FR-080 Live 模式

访问真实外部数据源，将选中记录增量写入研究工作集，并按来源 TTL 判断是否刷新。

#### FR-081 Fixture 模式

使用仓库内许可明确的少量固定样本，不访问网络，支持自动化测试和最小离线演示。

#### FR-082 Replay 模式

重放历史工具响应和 Agent 事件，保证 UI 演示稳定，并支持定位工作流回归。

三个模式对前端暴露相同的任务状态和事件协议。

## 9. Agent 设计

### 9.1 工作流原则

- 使用状态图和确定性边界控制流程。
- LLM 负责规划、分类、抽取、归纳和工具选择，不直接绕过服务写数据库。
- 所有工具输入输出通过 Pydantic 模型校验。
- 节点必须支持超时、重试、幂等和检查点。
- 大规模采集和高成本调用设置预算上限。
- 失败时保留已成功中间产物并明确降级状态。

### 9.2 Agent 角色

| Agent | 主要职责 | 关键输出 |
| --- | --- | --- |
| Supervisor | 驱动状态图、分配任务、控制预算与恢复 | 下一节点、运行状态、预算 |
| Research Planner | 拆解问题并生成混合检索策略 | 技术方向、关键词、CPC、排除条件 |
| Patent Agent | 检索、归并和分析专利 | 专利工作集、受让人、专利趋势 |
| Company Research Agent | 补充规范公司身份和公开信息 | 公司实体、外部 ID、事实声明 |
| Publication Agent | 检索论文和机构研究活动 | 论文、机构与主题关系 |
| News Agent | 发现新闻、官网内容和事件 | 新闻事件、时间线、候选实体 |
| Entity Resolution Agent | 生成实体匹配候选和解释 | 匹配候选、置信度、待审项 |
| Evidence Agent | 去重、冲突检测和可信度标注 | 可引用事实、冲突、缺失项 |
| Report Agent | 按固定结构综合报告 | 章节草稿、引用、后续建议 |

### 9.3 人工确认点

至少设置两个强制检查点：

1. 研究计划确认：正式采集前确认技术范围、查询和预算。
2. 报告前确认：查看候选企业、实体冲突、证据缺失和预期章节。

以下动作也需要确认：

- 大幅提高采集数量或模型预算。
- 合并中低置信度公司实体。
- 覆盖用户人工修订的报告结论。

## 10. 数据源方案

### 10.1 默认数据源

| 类型 | 默认来源 | MVP 用途 | 主要限制 |
| --- | --- | --- | --- |
| 全球公司身份 | GLEIF | LEI 实体、名称、地址、关系、实体消歧 | 不覆盖所有公司 |
| 美国公司 | SEC EDGAR | CIK、曾用名、申报和公开财务事实 | 主要覆盖 SEC 申报主体，需遵守速率与 User-Agent 要求 |
| 英国公司 | Companies House | 公司状态、地址、高管、申报历史 | 仅英国，需 API key 和限流 |
| 科研机构 | OpenAlex + ROR | 论文、机构、主题和外部 ID | 不是完整工商数据库 |
| 全球专利 | EPO OPS | 书目、专利族、部分全文和法律状态 | OAuth、配额、fair-use，字段覆盖不均 |
| 美国专利 | USPTO ODP / PatentsView | 美国专利与受让人消歧 | 新接口需 key，旧接口不可依赖 |
| 新闻 | GDELT | 新闻发现、趋势、实体和 URL | 噪声和重复较多，正文版权不属于 GDELT |
| 官方动态 | 公司或机构 RSS | 最新公告和新闻稿 | 覆盖不统一，正文仍受原站条款约束 |
| 人工核验 | Espacenet、Google Patents、CNIPA | 权威或易用的人工复核入口 | 不作为自动批量抓取 API |
| 历史网页兜底 | Common Crawl | 少量历史页面定位 | 内容仍受原网站权利约束，不做全量下载 |

OpenCorporates 暂不作为默认依赖。其免费方案的开放和 share-alike 条件需要单独评估；只有许可明确或购买适用方案后才接入。

### 10.2 中国数据边界

- 支持中文公司名、中文技术问题和中文报告。
- 可通过 EPO OPS 获取部分中国专利元数据，但不承诺字段完整或实时。
- CNIPA 和国家企业信用信息公示系统作为人工复核入口。
- 不自动绕过验证码或批量抓取页面。
- 企查查、天眼查等商业数据只能在取得正式 API 授权后作为新适配器接入。
- 报告必须显示公司身份和工商字段的覆盖限制。

## 11. 垂直领域公司—专利数据库

### 11.1 定位与目的

TechScout 在完整产品开发前先建设最小可用的垂直领域公司—专利数据库。该数据库不是临时缓存，而是产品持续积累的核心数据资产，用于：

- 在外部数据源不可用时提供可查询的数据底座。
- 支持按技术发现公司、按公司查询专利和跨公司比较。
- 持续积累公司别名、母子关系、专利权人和人工审核结果。
- 为实体消歧、检索和排序提供稳定输入。
- 建立固定评测基线。
- 避免每次开发都重复采集和清洗。

数据库的首批数据称为“种子数据集”。种子数据集不是手写 SQL 插入脚本，而是从官方 API、官方批量文件或人工确认清单构建的 JSONL/Parquet 数据包。

项目不在开发前建设全球全量公司和专利镜像库。完整产品开发的前置条件是最小数据底座通过 Data Gate，而不是数据库达到最终规模。

### 11.2 三层数据资产

| 数据层 | 定位 | 生命周期 |
| --- | --- | --- |
| 垂直领域主库 | 公司、专利族、权利主体、别名和关系等长期核心资产 | 持续增量更新 |
| 研究工作集 | 某次研究实际采用的公司、专利和证据 | 跟随研究运行版本化 |
| Fixture / Replay | 从主库裁剪或录制的稳定小样本 | 随测试基线版本化 |

主库负责稳定检索和跨任务复用；研究工作集负责解释某份报告使用了什么；Fixture/Replay 负责自动化测试和稳定演示。

### 11.3 首批领域

#### 领域一：AI 芯片 / 边缘推理加速

包含：

- 神经网络加速器、NPU、张量处理器。
- 推理芯片和边缘 AI SoC。
- 量化、稀疏计算和模型压缩的硬件实现。
- 存内计算、类脑或神经形态计算。
- 面向视觉、机器人、汽车和工业设备的低功耗推理。

排除：

- 没有 AI 特定权利要求的通用 CPU/GPU。
- 纯晶圆制造、封装、散热和一般存储器设计。
- 纯云调度、模型 API 和一般软件优化。

#### 领域二：工业视觉 / AI 质检

包含：

- AOI 自动光学检测。
- 表面缺陷、焊点、晶圆、织物、食品和零部件检测。
- 产线 2D/3D 视觉、视觉测量和异常检测。
- 工业相机、光源和边缘视觉控制器。
- 与抓取、分选和装配相关的工业视觉。

排除：

- 医学影像。
- 人脸识别和公共安防。
- 自动驾驶感知。
- 普通消费相机算法。
- 没有视觉技术资产的纯项目集成服务。

Data Spike 对两个领域使用同等规模样本，比较：

- 唯一专利受让人数量。
- 可映射到权威外部 ID 或官方域名的比例。
- 可获得产品、论文或新闻二次证据的比例。
- 头部受让人集中度。
- 大学、个人、IP 控股主体和误报占比。

若某个领域产出率明显不达标，可用“自动驾驶感知”替换。

### 11.4 建设规模

Data Spike 最小数据底座：

- 每个领域检索 200–500 件专利。
- 每个领域提取 20–50 个受让人候选。
- 至少一个领域核验 10–15 家公司。
- 跑通公司—专利关系、来源追溯和重复导入。

Data Gate 通过后，在 MVP 开发期间逐步扩充主库：

- 两个领域合计形成 200–500 个候选公司主体。
- 目标积累 5000–20000 个去重后的相关专利族。
- 记录公司别名、母子关系、IP 控股主体和权利转移关系。
- 为重点公司补充论文、官网、新闻和公开活动证据。

该规模是目标区间，不是必须一次性抓满的启动条件。实际规模受来源许可、API 配额、检索准确率和实体审核成本约束；优先保证关系正确和来源可追溯。

### 11.5 构建流程

```text
数据集查询配置
  ↓
公开 API / 官方文件 / 人工种子 CSV
  ↓
保存原始响应和来源元数据
  ↓
标准化、去重、专利族归并
  ↓
公司实体匹配与人工审核
  ↓
生成 JSONL / Parquet + manifest
  ↓
Loader 幂等写入 PostgreSQL 和 MinIO
  ↓
裁剪小型 Fixture 并生成评测集
```

建议命令边界：

```text
python -m intelligence.datasets build <domain> --version <version>
python -m intelligence.datasets review <dataset-version>
python -m intelligence.datasets load <dataset-version>
python -m intelligence.datasets verify <dataset-version>
```

### 11.6 数据集权威形式

- JSONL/Parquet：可移植的规范化数据。
- `manifest.json`：来源、查询、时间、许可、数量、schema 版本和 hash。
- 审核映射：人工确认的公司别名、母子关系和外部 ID。
- 构建日志：连接器版本、错误、过滤统计和字段覆盖。
- 导入程序：根据业务唯一键执行幂等 upsert。

数据库 dump 仅可作为本地快速恢复缓存，不作为数据集的权威来源。

### 11.7 Git 与本地数据分工

Git 仓库保存：

- 数据构建代码和查询配置。
- 数据 schema 和 manifest。
- 许可明确的人工审核映射。
- 数十条小型 Fixture 和评测期望。

Git 仓库不保存：

- 大型原始 API 响应、PDF 和网页快照。
- PostgreSQL、Redis 或 MinIO 数据卷。
- API key、模型密钥或访问令牌。
- 许可不明确或禁止再分发的内容。

垂直领域主库运行在本地 PostgreSQL 和 MinIO 中，其可重建输入保存在版本化数据目录。以后公开数据包时，只发布许可明确且允许再分发的字段。

## 12. 数据存储设计

### 12.1 存储分工

| 存储 | 内容 |
| --- | --- |
| PostgreSQL | 业务实体、规范化事实、来源索引、任务、状态、报告和审核记录 |
| pgvector | 报告实际使用的证据片段、专利摘要/权利要求和上传文档分块 |
| MinIO | HTML、PDF、XML、图片和较大的原始响应 |
| Redis | Celery 队列、短期缓存、限流状态和事件中转 |
| JSONL/Parquet | 垂直领域主库的版本化种子和增量数据包 |

### 12.2 核心数据实体

- `research_project`：研究项目。
- `research_run`：一次具体执行及版本信息。
- `research_direction`：技术方向和检索策略。
- `agent_checkpoint`：LangGraph 检查点。
- `agent_event`：用户可见事件和工程 trace 索引。
- `company_entity`：规范公司主体。
- `company_alias`：公司别名和历史名称。
- `external_identifier`：LEI、CIK、注册号、ROR 等。
- `entity_match`：实体匹配候选、特征、置信度和审核结果。
- `patent`：专利规范记录。
- `patent_family`：专利族。
- `patent_party`：申请人、受让人和发明人关系。
- `company_patent_relation`：规范公司与专利之间的角色、映射依据、置信度和审核状态。
- `publication`：论文和研究成果。
- `news_event`：新闻及公开事件。
- `source_record`：来源 URL、更新时间、hash、许可和原文对象 URI。
- `fact_claim`：结构化事实、有效时间、证据和推断标记。
- `evidence_chunk`：可引用与可检索的证据片段。
- `candidate_company`：某次研究中的候选企业、来源和排序特征。
- `report`、`report_section`、`citation`：报告、章节与引用。
- `dataset_version`：主库种子、增量包或 Fixture 版本。
- `user_feedback`：排除误报、确认实体和修订结论等反馈。

### 12.3 数据新鲜度与更新

- 每个连接器独立配置 TTL，不使用统一过期时间。
- 活跃研究项目按需增量更新。
- 垂直领域主库通过版本化种子包和增量包构建，固定评测绑定特定版本。
- 新数据先进入暂存区，通过去重和实体确认后进入规范表。
- 报告展示数据截止时间。
- 对来源更正、删除或法律状态变化保留版本历史。

## 13. 技术架构

### 13.1 总体架构

```text
React Web
  │ REST + SSE
  ▼
NestJS API
  ├─ 项目、报告、文件、运行状态
  ├─ 鉴权扩展边界
  ├─ SSE 事件转发
  └─ Python 服务网关
        │ HTTP + Redis/Celery
        ▼
Python Intelligence Service
  ├─ FastAPI
  ├─ LangGraph Agent 工作流
  ├─ 数据源 Connectors
  ├─ Crawlers / Parsers
  ├─ Entity / Evidence Extraction
  ├─ Dataset Builder
  ├─ Celery Workers
  └─ Evals

PostgreSQL + pgvector   Redis   MinIO
```

### 13.2 Monorepo 建议

```text
apps/
  web/                     React
  api/                     NestJS
services/
  intelligence/
    api/                   FastAPI
    agents/                LangGraph 工作流
    tools/                 Agent 工具
    connectors/            外部数据源适配器
    crawlers/              网页与文档采集
    extraction/            清洗、实体和事实抽取
    workers/               Celery 任务
    datasets/              主库种子与增量数据构建
    evals/                 Agent 评测
packages/
  contracts/               TypeScript API 与事件协议
  ui/                      React 通用组件
infra/                     Docker Compose 与部署配置
docs/                      PRD、架构和学习记录
```

MVP 保持一个 Python 服务并按模块隔离。只有接口稳定或扩展规模明显增加后，再将 crawler 拆成独立服务。

### 13.3 技术选型

| 层级 | 推荐技术 |
| --- | --- |
| Web | React、TypeScript、Vite、React Router、TanStack Query |
| 产品 API | NestJS、TypeScript、OpenAPI |
| Agent API | FastAPI、Pydantic |
| Agent 编排 | LangGraph |
| 异步任务 | Celery + Redis |
| 数据库 | PostgreSQL + pgvector |
| 对象存储 | MinIO，兼容 S3 API |
| 本地运行 | Docker Compose |
| 接口流式事件 | NestJS 向 React 提供 SSE |
| 模型接入 | OpenAI-compatible 适配层 |

### 13.4 模型策略

- 配置默认推理模型、低成本模型和嵌入模型。
- 通过统一适配层隔离供应商 SDK。
- MVP 不实现自动模型路由。
- 模型配置不能包含在源码中。
- 每次运行记录模型、提示词版本、token、费用和耗时。
- 对结构化输出执行 schema 校验和有限重试。
- 支持用 Fixture 模型响应执行离线测试。

## 14. 非功能需求

### 14.1 性能和预算

单次默认研究预算：

- 1–3 个技术子方向。
- 最多 10 家候选企业。
- 每个方向最多分析 50 件高相关专利。
- 最多处理 30 条近期新闻或活动线索。
- 目标完成时间 5–10 分钟。
- 月度外部 API 和模型预算目标为人民币 200–500 元。

预算达到阈值时暂停新增调用，并请求用户确认。

### 14.2 可靠性

- 单个非核心数据源失败时继续任务，并标记降级。
- 专利主线完全不可用时将运行标记为“部分完成”。
- SSE 断线后根据事件序号恢复。
- 所有长任务支持超时、取消和有限重试。
- 所有写入操作具备幂等键。

### 14.3 安全

- 密钥只通过环境变量或本地密钥管理提供。
- 上传文件限制类型和大小，文件名不直接作为存储路径。
- 外部 URL 采集防范 SSRF，仅允许 HTTP/HTTPS 并限制私网地址。
- HTML 清洗后再展示，避免脚本注入。
- 日志中不记录密钥、完整提示词私密内容或敏感上传资料。
- 用户删除资料时同步删除其向量和派生数据。

### 14.4 合规与来源治理

- 每个连接器维护许可和采集策略说明。
- 保存来源 URL、时间、hash、内容类型和允许的展示范围。
- 新闻正文默认不长期保存。
- 不绕过访问控制，不伪造 User-Agent 身份。
- 对允许再分发和仅允许本地使用的数据进行分级。
- 导出报告只包含必要引用，不打包受限制的完整原文。

### 14.5 可维护性

- 前后端共享事件和 DTO 契约，接口变更可检测。
- 每个连接器有独立契约测试和录制样本。
- Agent 节点保持小职责、显式输入输出和独立评测。
- 数据 schema、提示词、工作流和数据集均有版本号。

## 15. 状态与失败模型

研究运行主要状态：

```text
draft
  → planning
  → awaiting_plan_approval
  → collecting
  → resolving_entities
  → analyzing_evidence
  → awaiting_report_approval
  → generating_report
  → completed
```

任一执行状态还可进入：

- `partially_completed`：部分来源失败但已有可用结果。
- `failed`：无法继续且没有足够结果。
- `cancelled`：用户取消。
- `paused_budget`：达到费用或调用预算，等待确认。

失败记录必须包含错误分类、可否重试、失败节点、影响范围和已保留产物。

## 16. 评测与验收

### 16.1 固定评测集

建立 10–20 个固定研究案例，覆盖：

- AI 芯片和工业视觉两个种子领域。
- 同名公司、曾用名、子公司和 IP 控股主体。
- 专利族重复、字段缺失和法律状态冲突。
- 新闻实体误判、重复报道和来源冲突。
- 数据源超时、限流和部分不可用。
- 中文问题、英文来源和中文报告。

### 16.2 初始质量指标

| 指标 | MVP 目标 |
| --- | --- |
| 结构化输出成功率 | ≥ 95% |
| 报告关键事实引用覆盖率 | ≥ 90% |
| 引用与事实一致率 | ≥ 85% |
| 已知公司召回率 | 达到 Data Spike 建立的基线 |
| 无证据推断标记率 | 100% |
| 任务刷新后恢复 | 关键场景全部通过 |
| Fixture/Replay 演示成功率 | 100% |
| 单次默认运行 | 不超过配置的时间与费用上限 |

指标是起始目标。Data Spike 后先记录真实基线，再调整不现实或区分度不足的阈值。

### 16.3 MVP 验收场景

完整演示至少通过以下场景：

1. 用户创建“工业视觉边缘推理”研究项目。
2. Planner 生成可编辑的方向、CPC 和关键词策略。
3. 用户确认后启动 Live 或 Fixture 采集。
4. 系统展示专利、论文和新闻工具调用进度。
5. 系统发现候选企业并完成至少一批实体匹配。
6. 用户查看并处理一个待确认实体。
7. 系统生成最多 10 家候选企业长名单和排序理由。
8. 用户选择一家企业生成带引用报告。
9. 报告显示至少一个冲突、缺失或推断标记。
10. 用户刷新页面后任务和报告仍可恢复。
11. 用户导出 Markdown 报告。
12. 同一场景可以用 Replay 模式稳定重放。

## 17. 实施计划

### 阶段 0：最小数据底座与 Data Gate（第 1–2 周）

目标：先建立最小可查询的公司—专利数据库并证明数据链路可行。完整 React 工作台和 Agent 主链不得早于 Data Gate 启动；用于验证数据的最小脚本、Loader、数据库 migration 和最小报告生成不受此限制。

- 申请并验证 EPO、USPTO 等必要凭证。
- 实现 GLEIF、EPO、OpenAlex、GDELT 的最小连接器。
- 为两个候选领域抽取同等规模专利样本。
- 比较受让人数量、实体映射率、证据覆盖和误报率。
- 跑通原始快照、规范化、实体审核和入库。
- 固化第一版垂直领域主库、Fixture 和 Replay。
- 生成一份最小带引用报告。

Data Gate 退出条件：

- 至少一个领域获得 200 件以上有效专利。
- 至少发现并核验 10 家以上候选企业。
- 可以按技术查询公司、按公司查询关联专利。
- 公司—专利关系能够追溯到原始来源和匹配依据。
- 同一数据集可重复导入且不产生重复记录。
- 能生成一份关键事实带引用的最小报告。

Data Gate 通过后进入阶段 1；垂直领域主库扩充与产品开发并行进行。

### 阶段 1：工程骨架（第 3–4 周）

- 建立 monorepo 和 Docker Compose。
- 初始化 React、NestJS、FastAPI、PostgreSQL、Redis、MinIO。
- 定义共享 DTO、任务状态和 SSE 事件协议。
- 实现研究项目、运行状态和数据集版本模型。
- 接入模型适配层和基础 trace。

### 阶段 2：Agent 主链（第 5–6 周）

- 实现 Planner、Patent、Company、Entity 和 Evidence 节点。
- 接入 LangGraph 检查点、暂停、恢复和人工确认。
- 实现任务预算、超时、软降级和幂等。
- 形成候选企业长名单与可解释排序。

### 阶段 3：产品闭环（第 7–8 周）

- 完成研究工作台、任务时间线和企业探索页面。
- 实现企业详情、证据抽屉和报告生成。
- 支持文件上传、追问、人工修订和 Markdown 导出。
- 完成 Live、Fixture 和 Replay 模式切换。

### 阶段 4：评测与作品化（第 9–10 周）

- 建立 10–20 个固定评测案例。
- 完成引用一致性、实体匹配和回归评测。
- 优化成本、时延、错误提示和可观察性。
- 补充架构说明、演示脚本和学习复盘。
- 打包本地一键启动流程和私有演示环境。

## 18. Agent 学习路线

项目实施与学习目标对应如下：

| 阶段 | 学习主题 | 项目实践 |
| --- | --- | --- |
| 1 | Tool Calling、结构化输出 | 数据连接器工具、Pydantic schema、错误重试 |
| 2 | RAG 与文档解析 | PDF/网页分块、pgvector、混合检索和引用 |
| 3 | 状态工作流 | LangGraph 节点、检查点、暂停和恢复 |
| 4 | 多 Agent 协作 | Supervisor 与专业 Agent 的显式交接 |
| 5 | Human-in-the-loop | 研究计划、实体匹配和报告前确认 |
| 6 | 可观测性 | trace、token、费用、耗时和工具错误 |
| 7 | Agent 评测 | 固定数据集、引用一致性和回归测试 |
| 8 | 工具协议 | 将数据连接器抽象为可扩展工具，后续评估 MCP |

学习原则：每引入一个 Agent 概念，都必须对应可测试的产品问题；不为了展示名词而增加无必要的自治和复杂度。

## 19. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 数据源限流或接口迁移 | Live 任务失败 | 适配器隔离、健康检查、Fixture/Replay、缓存和软降级 |
| 数据许可不明确 | 无法保存或公开数据 | 来源策略、最小引用、许可分级和本地数据包 |
| 中国公司数据不足 | 报告字段不完整 | 明示覆盖边界、用户上传、后续合法商业 API |
| 专利权人映射错误 | 候选企业和结论失真 | 强标识优先、中低置信度人工审核、保留映射证据 |
| 头部大公司淹没结果 | 难发现中小企业 | 受让人集中度评测、分层排序、新闻/论文补充发现 |
| LLM 幻觉 | 生成错误事实 | 证据优先、引用校验、推断标记、禁止补写缺失数据 |
| 多服务复杂度过高 | 延误 MVP | Python 单服务模块化、单用户、本地优先、延后拆分 |
| 数据工程吞噬 Agent 学习时间 | 主流程无法完成 | 以 Data Gate 限制前置规模，通过后让主库扩充与产品并行 |
| 成本和延迟失控 | 无法日常使用 | 默认预算、低成本模型、缓存、批处理和人工确认 |
| clean-room 边界模糊 | 个人项目知识产权风险 | 使用新名称和新实现，不复制公司资产或私有信息 |

## 22. 当前仓库观察与新项目关系

从当前仓库可以观察到的通用产品事实包括：

- 当前代码是 React/TypeScript/Vite 前端，不包含可复用的后端、数据库或 Agent 实现。
- 现有交互包含研究目标拆解、专利和活动线索扫描、企业长名单、企业库和报告库。
- 现有前端通过 SSE 展示联网检索、推理摘要和结构化结果。
- 专利权人与企业候选高度相关，公司和新闻数据的真实供应商无法从仓库确认。
- 跟踪预警页面是静态原型，不能视为已验证需求。

TechScout 只借鉴这些通用问题和工作流经验。其数据模型、接口、Agent、提示词、评分、品牌和实现均应重新设计。

## 23. 最终范围基线

在开始开发前，以下决策视为已确认：

- 个人独立学习与作品演示优先。
- 使用 React + NestJS + Python 完成重写。
- Python 负责 Agent、采集、解析与数据集构建；NestJS 负责产品后端。
- 使用可控状态图和专业 Agent，不使用无限自主 Agent 群聊。
- 先建设最小垂直领域公司—专利数据库，通过 Data Gate 后再开发完整产品。
- 主库持续增量扩充，研究工作集和 Fixture/Replay 分层管理；不建设全球全量镜像库。
- 首批领域为 AI 芯片/边缘推理加速和工业视觉/AI 质检。
- 关键事实必须有证据，模型推断必须显式标记。
- MVP 单用户、本地优先，并在 8–10 周内形成可稳定演示的闭环。
