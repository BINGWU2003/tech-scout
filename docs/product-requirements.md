## 1. 文档目的

本文档定义 TechScout 的产品目标、MVP 范围、数据策略、Agent 工作流、技术边界、验收标准和学习路线，用于指导后续架构设计与实现。

TechScout 借鉴技术情报类产品的通用业务流程，但采用 clean-room 方式独立设计和实现。当前公司项目仓库仅用于理解通用业务场景，不直接复制其源码、品牌、文案、私有接口、私有数据、提示词、评分算法或未知的后端实现。

本文档不是当前 TechAlpha 前端的改造方案，也不承诺替换任何公司内部或生产系统。

## 2. 背景与问题

硬科技研究往往需要同时处理技术分类、专利、公司主体、论文、新闻和公开活动等异构信息。传统人工流程存在以下问题：

- 研究问题难以快速拆解为稳定、可复用的检索策略。
- 专利申请人、公司别名、母子公司和历史名称难以统一。
- 数据来源分散，人工收集和去重成本高。
- 研究结论容易脱离原始证据，无法追溯或复核。
- 一次性报告难以复现，换模型、换数据后缺少回归评测。
- 在线数据 API 的限流、接口迁移和可用性会让运行结果不稳定，难以复现。

TechScout 先通过官方批量文件构建本地垂直领域公司—专利数据库，再使用可控的多 Agent 工作流，将“研究规划—本地检索—证据核验—公司发现—报告生成”串成一个可观察、可恢复、可评测的研究过程。

## 3. 产品定位

### 3.1 一句话定义

TechScout 是一个面向产业研究员和技术投资研究者的 AI 技术情报平台：用户输入技术方向，系统利用自建的垂直领域公司—专利数据库发现候选企业，并生成带证据引用的结构化研究报告。

### 3.2 目标用户

MVP 主要服务以下用户：

- 希望学习 Agent 工程、数据采集和 RAG 的开发者本人。
- 需要演示完整 AI 工程能力的面试官、同事或技术评审者。
- 以技术路线和企业线索为关注点的产业研究员或技术投资研究者。

MVP 按单用户设计，不建设团队、多租户和复杂权限系统。

### 3.3 产品边界

TechScout 是技术情报和研究辅助工具，不提供买入、卖出、估值或其他投资建议。所有模型生成内容均需区分来源事实与模型推断。

## 4. 项目目标与非目标

### 4.1 MVP 目标

1. 跑通从技术问题到候选企业和研究报告的完整纵向链路。
2. 从官方批量文件构建完全本地运行的数据底座，产品运行时不调用第三方数据 API。
3. 实现可控、可恢复的多 Agent 工作流，而非不可预测的自由 Agent 群聊。
4. 为关键事实提供来源、引用片段、采集时间和可信度。
5. 展示 Agent 的工具调用、阶段状态、成本、耗时和失败信息。
6. 建立固定评测集，使提示词、模型或工作流调整可以量化回归。
7. 覆盖 TypeScript 全栈、Python Agent、离线 ETL、数据工程和可观测性等学习目标。

### 4.2 MVP 非目标

- 不镜像全球全量专利全文、论文全文或新闻正文，只保留指定领域的公司、专利和关系。
- MVP 不进行在线公司、专利、论文、新闻或网页查询。
- 不承诺完整覆盖中国工商、融资、招投标或专利法律数据。
- 不绕过登录、验证码、付费墙、robots 或其他技术保护。
- 不提供精确但缺乏依据的“投资潜力 87 分”等综合评分。
- 不实现多租户、团队协作、套餐、计费和复杂权限。
- 不实现生产级高可用、跨区域容灾和大规模分布式爬取。
- 不在 MVP 中实现定时跟踪预警。
- 不同时引入多个 Agent 框架进行横向比较。
- 不直接展示模型私有思维链。

## 5. 成功标准

当用户输入一个技术方向后，系统能够：

1. 生成 1–3 个可编辑的技术子方向和检索策略。
2. 在用户确认后调用本地 catalog 检索工具执行研究。
3. 从本地专利申请人、受让人和用户资料中发现候选企业。
4. 对公司别名、外部 ID 和专利权人进行实体消歧。
5. 为最多 10 家候选企业给出可解释的排序和匹配理由。
6. 生成包含公司身份、专利布局、风险和信息缺口的中文报告。
7. 对报告关键事实提供可展开的证据引用。
8. 在刷新页面或本地检索节点失败后恢复任务，并支持重试或取消。
9. 在 Fixture 或 Replay 模式下稳定复现完整演示。

## 6. 核心概念

| 概念                    | 定义                                                                                    |
| ----------------------- | --------------------------------------------------------------------------------------- |
| 研究项目                | 用户围绕一个技术问题发起的一次持续研究容器                                              |
| 研究运行                | 研究项目下的一次具体 Agent 执行，绑定模型、提示词和数据版本                             |
| 技术方向                | Agent 从原始问题拆解出的可检索子主题                                                    |
| 检索策略                | 关键词、CPC 分类、排除条件、时间和区域等组合                                            |
| 候选企业                | 从本地专利申请人、受让人或用户清单发现的待核验主体                                      |
| 规范实体                | 经过别名合并并关联外部 ID 的公司、机构或个人                                            |
| 事实声明                | 从来源中抽取的结构化主张，包含证据和有效时间                                            |
| 证据                    | 支持事实或推断的原始来源、片段、URL 与采集记录                                          |
| Bronze 公司参考数据     | 从 GLEIF、SEC 等官方批量文件转换的本地 Parquet，用于离线实体匹配，不全部进入 PostgreSQL |
| 垂直领域公司—专利数据库 | 持续积累特定 AI 领域的公司、专利、主体关系和来源历史，是产品核心数据资产                |
| 种子数据集              | 垂直领域数据库的首个可版本化数据包，用于初始化、复现和扩充主库                          |
| Fixture 模式            | 使用仓库内极小固定样本执行测试和演示                                                    |
| Replay 模式             | 重放已记录的工具返回和 Agent 事件，不访问外部服务                                       |
| Catalog 模式            | 只查询最新已发布的本地 PostgreSQL catalog，不访问第三方数据服务                         |

## 7. 核心用户流程

```text
创建研究项目
  ↓
输入技术方向或研究问题
  ↓
Planner 生成技术子方向、CPC 与关键词检索策略
  ↓
用户编辑并确认研究计划
  ↓
并行检索专利、论文、公司和新闻
  ↓
提取专利受让人、论文机构和新闻实体
  ↓
公司实体消歧与人工确认
  ↓
Evidence Agent 去重、冲突检测、可信度标注
  ↓
生成候选企业长名单及可解释排序
  ↓
用户选择企业并补充调查
  ↓
Report Agent 生成带引用报告
  ↓
用户追问、修订并导出 Markdown
```

## 8. 功能需求

### 8.1 研究项目与任务

#### FR-001 创建研究项目

用户可以输入自然语言研究问题创建项目，例如“寻找适用于工业视觉质检的边缘 AI 推理芯片公司”。

验收要求：

- 输入不能为空，并设置合理的长度限制。
- 创建后立即生成唯一项目 ID 和初始研究运行。
- 项目保存标题、原始问题、创建时间、更新时间和状态。
- 用户可以重命名、归档或删除项目。

#### FR-002 项目状态恢复

- 刷新页面后恢复到最后查看的研究阶段。
- 每个长任务保存检查点和最近事件序号。
- 用户可以取消正在执行的运行。
- 失败节点可单独重试，不重复覆盖已经成功的数据。
- 同一幂等键不得创建重复的采集或报告任务。

### 8.2 研究规划

#### FR-010 自动拆解技术方向

Planner Agent 将原始问题拆成 1–3 个技术子方向，每个方向包括：

- 名称和范围说明。
- 包含关键词和排除关键词。
- 建议 CPC 分类及解释。
- 时间、区域和本地数据集范围。
- 潜在歧义与漏检风险。

#### FR-011 人工确认计划

- 用户可增删、编辑和排序技术方向。
- 用户可修改关键词、CPC、排除条件和分析预算。
- 正式查询本地 catalog 前必须确认研究计划。
- 重新生成计划时保留历史轮次，便于比较。

### 8.3 本地 Catalog 检索

#### FR-020 数据集版本选择

- 每次研究运行绑定一个已经发布的 `dataset_release`。
- 默认使用最新已发布版本，固定评测可以选择历史版本。
- 运行期间不得切换数据版本。
- 报告显示数据截止时间、来源文件和领域规则版本。

#### FR-021 本地专利检索

MVP 只查询 PostgreSQL catalog，支持：

- 按关键词、CPC、申请人、受让人和时间范围检索。
- 获取出版号、申请号、标题、摘要、日期、申请人、受让人、发明人、CPC 和可用专利族。
- 根据本地 `patent_domain_match` 和 Agent 分析计算相关性，并保留理由。
- 对同一专利族进行归并，避免重复计数。
- 展示来源文件、release 和原始记录定位信息。
- 对来源字段缺失进行明确标注，禁止模型补写。

#### FR-022 本地公司检索

MVP 支持通过公司名称、别名和外部 ID 查询：

- 规范名称、司法辖区和已导入的公司字段。
- LEI、CIK、Companies House number 等外部标识。
- 已确认的曾用名、证券代码和母子关系。
- 公司—专利关系的角色、匹配依据、置信度和审核状态。

公司未匹配到本地参考数据时允许继续分析，但必须标记为未核验主体。

#### FR-023 本地证据边界

- Agent 只能引用 catalog、用户上传文件和当前研究工作集中的内容。
- MVP 不在线查询新闻、论文、网页、公司或专利服务。
- 数据库没有的事实必须标记为缺失，不得使用模型记忆补全。
- 新闻、论文和网页证据只有在未来形成合法离线数据包后才可加入 catalog。

### 8.4 用户资料导入

#### FR-030 上传资料

用户可以补充：

- PDF：论文、专利、公司报告。
- CSV：公司或专利种子清单。

要求：

- 设置单文件大小、单次数量和文件类型限制。
- 对文件进行 hash 去重和恶意内容基础检查。
- 所有上传来源标记为“用户提供”。
- 解析失败不影响其他研究流程。
- 用户可删除文件及其派生分块和向量。

### 8.5 实体消歧

#### FR-040 公司实体匹配

Entity Resolution 节点综合以下特征：

- 规范化名称和别名相似度。
- 注册号、LEI、CIK、ROR 等强标识。
- 官网域名、地址和司法辖区。
- 专利受让人、论文机构和新闻中的上下文。
- 母公司、子公司、历史名称和并购关系。

匹配结果分为：

- 已自动确认：强标识一致且无冲突。
- 待人工确认：中等置信度或存在多个候选。
- 暂不合并：证据不足或冲突明显。

系统必须记录匹配特征、置信度、确认者和确认时间，禁止仅凭 LLM 自由文本合并实体。

### 8.6 候选企业发现与排序

#### FR-050 多渠道发现

候选企业来自以下集合的并集：

- 专利申请人和受让人。
- OpenAlex/ROR 企业研究机构。
- 新闻、官网和公开活动中的企业实体。
- 用户上传的公司清单。

每家企业显示发现渠道，不宣称候选名单覆盖全部市场。

#### FR-051 可解释排序

MVP 不生成伪精确的综合投资分。排序指标至少包括：

- 与技术方向的语义及规则匹配程度。
- 相关专利数量、时间趋势和专利族分布。
- 专利法律状态和重点专利证据。
- 论文、产品和新闻的交叉证据。
- 信息完整度、新鲜度和来源可信度。
- 冲突、缺失与实体匹配风险。

用户能够展开查看排序理由和底层证据。

#### FR-052 企业长名单

- 默认最多保留 10 家候选企业。
- 支持按技术方向、发现来源、区域和证据完整度筛选。
- 支持关注企业并进入公司详情。
- 支持排除误报，并将用户反馈保存到评测数据中。

### 8.7 公司详情与研究报告

#### FR-060 公司详情

公司详情至少包含：

- 规范身份和别名。
- 与研究方向的匹配摘要。
- 相关专利、专利族和时间趋势。
- 论文与科研活动。
- 新闻及公开事件时间线。
- 数据来源、冲突、缺失项和更新时间。

#### FR-061 报告生成

报告采用固定主结构：

1. 研究问题与范围。
2. 技术方向与检索策略。
3. 候选企业长名单。
4. 企业与技术匹配证据。
5. 专利布局、趋势和重点专利。
6. 新闻、论文及公开活动时间线。
7. 风险、来源冲突和信息缺口。
8. 综合结论与后续调查建议。
9. 完整来源列表和执行记录。

#### FR-062 引用与推断标记

- 关键事实必须关联至少一个来源片段。
- 每条引用显示来源、URL、采集时间和原文。
- 模型归纳或推断必须明确标记，不能伪装为来源原文。
- 来源冲突时同时呈现不同说法，不静默选择一方。
- 用户可以从报告跳转到证据详情或原始页面。

#### FR-063 报告交互与导出

- 支持展开或折叠章节。
- 支持围绕已有证据追问。
- 支持人工修订报告正文。
- 保存自动生成版本和人工修订版本。
- MVP 支持 Markdown 导出，PDF 导出进入第二阶段。

### 8.8 执行轨迹与可观测性

#### FR-070 用户可见轨迹

前端展示：

- 当前工作阶段和整体进度。
- Agent 和工具名称。
- 使用的检索式、CPC 和数据源。
- 找到、过滤和采用的证据数量。
- 结构化判断理由摘要。
- 重试、降级、取消和人工确认记录。

不展示模型私有思维链。

#### FR-071 工程观测

每次 Agent 运行记录：

- 模型供应商、模型名和参数。
- 提示词和工作流版本。
- 输入输出 token、费用与耗时。
- 工具调用输入输出摘要和错误。
- 状态转换、重试次数和检查点。
- 数据集版本与引用来源。

### 8.9 Live、Fixture 与 Replay

#### FR-080 Live 模式（MVP 后）

Live 外部检索不属于当前 MVP。后续引入时，访问真实外部数据源，将选中记录增量写入研究工作集，并按来源 TTL 判断是否刷新；必须同时实现许可、限流、来源审计和失败策略。

#### FR-081 Fixture 模式

使用仓库内许可明确的少量固定样本，不访问网络，支持自动化测试和最小离线演示。

#### FR-082 Replay 模式

重放历史工具响应和 Agent 事件，保证 UI 演示稳定，并支持定位工作流回归。

MVP 默认使用本地 Catalog；Fixture 和 Replay 用于自动化测试及稳定演示。未来引入 Live 后，三个执行模式对前端暴露相同的任务状态和事件协议。

## 9. Agent 设计

### 9.1 工作流原则

- 使用状态图和确定性边界控制流程。
- LLM 负责规划、分类、抽取、归纳和工具选择，不直接绕过服务写数据库。
- 所有工具输入输出通过 Pydantic 模型校验。
- 节点必须支持超时、重试、幂等和检查点。
- 大规模采集和高成本调用设置预算上限。
- 失败时保留已成功中间产物并明确降级状态。

### 9.2 Agent 角色

| Agent                   | 主要职责                             | 关键输出                        |
| ----------------------- | ------------------------------------ | ------------------------------- |
| Supervisor              | 驱动状态图、分配任务、控制预算与恢复 | 下一节点、运行状态、预算        |
| Research Planner        | 拆解问题并生成混合检索策略           | 技术方向、关键词、CPC、排除条件 |
| Patent Agent            | 检索、归并和分析专利                 | 专利工作集、受让人、专利趋势    |
| Company Research Agent  | 补充规范公司身份和公开信息           | 公司实体、外部 ID、事实声明     |
| Publication Agent       | 检索论文和机构研究活动               | 论文、机构与主题关系            |
| News Agent              | 发现新闻、官网内容和事件             | 新闻事件、时间线、候选实体      |
| Entity Resolution Agent | 生成实体匹配候选和解释               | 匹配候选、置信度、待审项        |
| Evidence Agent          | 去重、冲突检测和可信度标注           | 可引用事实、冲突、缺失项        |
| Report Agent            | 按固定结构综合报告                   | 章节草稿、引用、后续建议        |

### 9.3 人工确认点

至少设置两个强制检查点：

1. 研究计划确认：正式采集前确认技术范围、查询和预算。
2. 报告前确认：查看候选企业、实体冲突、证据缺失和预期章节。

以下动作也需要确认：

- 大幅提高采集数量或模型预算。
- 合并中低置信度公司实体。
- 覆盖用户人工修订的报告结论。

## 10. 数据源方案

### 10.1 默认数据源

| 类型         | 默认来源                                | MVP 用途                                                         | 主要限制                                                |
| ------------ | --------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------- |
| 全球公司身份 | GLEIF Golden Copy + API                 | 全量导入 LEI 实体、名称、地址和关系，API 用于增量核验            | 不覆盖所有公司，但官方批量数据许可清晰                  |
| 美国公司     | SEC Company Tickers + EDGAR Bulk/API    | 全量导入 CIK、名称、ticker、交易所，再按需补充申报和公开财务事实 | 主要覆盖 SEC 申报主体，API 需遵守速率与 User-Agent 要求 |
| 英国公司     | Companies House Free Company Data + API | 可选全量导入英国公司基础 CSV，API 用于详情和增量                 | 数据量较大、仅英国，需独立评估本地存储和更新成本        |
| 科研机构     | OpenAlex + ROR                          | 论文、机构、主题和外部 ID                                        | 不是完整工商数据库                                      |
| 全球专利     | EPO OPS                                 | 书目、专利族、部分全文和法律状态                                 | OAuth、配额、fair-use，字段覆盖不均                     |
| 美国专利     | USPTO ODP / PatentsView                 | 美国专利与受让人消歧                                             | 新接口需 key，旧接口不可依赖                            |
| 新闻         | GDELT                                   | 新闻发现、趋势、实体和 URL                                       | 噪声和重复较多，正文版权不属于 GDELT                    |
| 官方动态     | 公司或机构 RSS                          | 最新公告和新闻稿                                                 | 覆盖不统一，正文仍受原站条款约束                        |
| 人工核验     | Espacenet、Google Patents、CNIPA        | 权威或易用的人工复核入口                                         | 不作为自动批量抓取 API                                  |
| 历史网页兜底 | Common Crawl                            | 少量历史页面定位                                                 | 内容仍受原网站权利约束，不做全量下载                    |

OpenCorporates 暂不作为默认依赖。其免费方案的开放和 share-alike 条件需要单独评估；只有许可明确或购买适用方案后才接入。

### 10.2 中国数据边界

- 支持中文公司名、中文技术问题和中文报告。
- 可通过 EPO OPS 获取部分中国专利元数据，但不承诺字段完整或实时。
- CNIPA 和国家企业信用信息公示系统作为人工复核入口。
- 不自动绕过验证码或批量抓取页面。
- 企查查、天眼查等商业数据只能在取得正式 API 授权后作为新适配器接入。
- 报告必须显示公司身份和工商字段的覆盖限制。

## 11. 垂直领域公司—专利数据库

### 11.1 定位与目的

TechScout 在完整产品开发前先建设最小可用的垂直领域公司—专利数据库。该数据库不是临时缓存，而是产品持续积累的核心数据资产，用于：

- 在外部数据源不可用时提供可查询的数据底座。
- 支持按技术发现公司、按公司查询专利和跨公司比较。
- 持续积累公司别名、母子关系、专利权人和人工审核结果。
- 为实体消歧、检索和排序提供稳定输入。
- 建立固定评测基线。
- 避免每次开发都重复采集和清洗。

数据库的首批数据称为“种子数据集”。种子数据集不是手写 SQL 插入脚本，而是从官方 API、官方批量文件或人工确认清单构建的 JSONL/Parquet 数据包。

项目允许在开发前全量导入官方提供、许可清晰且规模可管理的公司身份数据，形成实体匹配参考层；但不建设全球全量专利、论文和新闻镜像库。完整产品开发的前置条件是最小数据底座通过 Data Gate，而不是数据库达到最终规模。

### 11.2 四层数据资产

| 数据层           | 定位                                                 | 生命周期                 |
| ---------------- | ---------------------------------------------------- | ------------------------ |
| 公司身份参考库   | GLEIF、SEC 和可选 Companies House 的官方批量主体数据 | 按官方快照或增量周期更新 |
| 垂直领域主库     | 公司、专利族、权利主体、别名和关系等长期核心资产     | 持续增量更新             |
| 研究工作集       | 某次研究实际采用的公司、专利和证据                   | 跟随研究运行版本化       |
| Fixture / Replay | 从主库裁剪或录制的稳定小样本                         | 随测试基线版本化         |

身份参考库负责提供稳定的法律实体和外部 ID；垂直领域主库负责技术公司发现、公司—专利关系和跨任务复用；研究工作集负责解释某份报告使用了什么；Fixture/Replay 负责自动化测试和稳定演示。

### 11.3 首批领域

#### 领域一：AI 芯片 / 边缘推理加速

包含：

- 神经网络加速器、NPU、张量处理器。
- 推理芯片和边缘 AI SoC。
- 量化、稀疏计算和模型压缩的硬件实现。
- 存内计算、类脑或神经形态计算。
- 面向视觉、机器人、汽车和工业设备的低功耗推理。

排除：

- 没有 AI 特定权利要求的通用 CPU/GPU。
- 纯晶圆制造、封装、散热和一般存储器设计。
- 纯云调度、模型 API 和一般软件优化。

#### 领域二：工业视觉 / AI 质检

包含：

- AOI 自动光学检测。
- 表面缺陷、焊点、晶圆、织物、食品和零部件检测。
- 产线 2D/3D 视觉、视觉测量和异常检测。
- 工业相机、光源和边缘视觉控制器。
- 与抓取、分选和装配相关的工业视觉。

排除：

- 医学影像。
- 人脸识别和公共安防。
- 自动驾驶感知。
- 普通消费相机算法。
- 没有视觉技术资产的纯项目集成服务。

Data Spike 对两个领域使用同等规模样本，比较：

- 唯一专利受让人数量。
- 可映射到权威外部 ID 或官方域名的比例。
- 可获得产品、论文或新闻二次证据的比例。
- 头部受让人集中度。
- 大学、个人、IP 控股主体和误报占比。

若某个领域产出率明显不达标，可用“自动驾驶感知”替换。

### 11.4 建设规模

Data Spike 和 Data Gate 已完成。当前可验证基线为：

- AI 芯片与边缘推理专利 1,882 件。
- 工业视觉与 AI 质检专利 981 件。
- 共 2,863 件去重美国授权专利。
- 731 个公司候选全部完成自动匹配或终态审核，活动队列为 0。
- Catalog `2026-09-v6` 已发布，最小研究报告关键事实引用覆盖率为 100%。

这些数量描述当前数据范围，不是市场份额或最终产品容量目标。详细行数、来源和限制见[数据底座参考](./database-and-data-status.md)。后续只在明确产品功能需要时增加摘要、权利要求、专利族、新闻、论文或财务数据。

### 11.5 构建流程

离线数据工程独立位于 `pipelines/data-foundation`，负责 Raw → Bronze → Silver → Catalog 和固定报告，不进入在线请求链。完整目录、命令和发布步骤见[数据获取与发布指南](./data-acquisition-guide.md)，组件边界见[产品与系统架构](./architecture.md)。

### 11.6 数据集权威形式

- JSON、CSV 和 Parquet：可移植的版本化数据。
- `manifest.json`：来源、规则、时间、许可、数量、schema 和 hash。
- Review release：审核决定、官方证据和附件 hash。
- PostgreSQL Catalog：产品查询层，由已验证 Silver 幂等发布。

数据库 dump 仅可作为本地快速恢复缓存，不作为数据集的权威来源。

### 11.7 Git 与本地数据分工

Git 保存代码、migration、版本化规则、测试和文档；大型 Raw、Bronze、Silver、审核附件、报告 release 和数据库备份保存在 `D:\files\project-data`。密钥、数据库密码和许可不允许再分发的内容不得进入 Git。

## 12. 数据存储设计

产品必须区分两类数据：

- `catalog`：已发布的公司、专利、领域、审核和来源事实；由离线 Data Foundation 发布，运行时只读。
- `app`：未来的用户、项目、任务、Agent 运行和保存报告；由 NestJS 拥有写入权。

当前 `catalog` 已实现，`app` schema 尚无表。Redis、MinIO、pgvector 不是 MVP 的默认依赖，只在队列、对象存储或语义检索出现真实需求后引入。完整表结构和当前行数见[数据底座参考](./database-and-data-status.md)，所有权和演进原则见[产品与系统架构](./architecture.md)。

所有报告必须展示数据 release 和截止时间；来源更正或规则变化通过新 release 处理，不原地覆盖历史数据包。

## 13. 技术架构

详细架构已经独立到[产品与系统架构](./architecture.md)，框架、数据库客户端、契约和测试工具见[技术选型](./technology-stack.md)。本 PRD 只保留以下产品级约束：

- 浏览器只调用 NestJS。
- NestJS 负责产品 API、鉴权、业务状态和 `app` schema。
- Python Intelligence 负责 Agent、研究工作流、模型和工具，只读 Catalog。
- 离线 Data Foundation 独立位于 `pipelines/data-foundation`，不进入在线请求链。
- MVP 默认查询本地 Catalog；Live 外部检索延后。
- Redis、Celery、MinIO 和 pgvector 按真实需求引入，不作为启动条件。
- 模型配置和凭据不能进入源码；结构化输出必须校验并记录版本、成本和耗时。

## 14. 非功能需求

### 14.1 性能和预算

单次默认研究预算：

- 1–3 个技术子方向。
- 最多 10 家候选企业。
- 每个方向最多分析 50 件高相关专利。
- 最多处理 30 条近期新闻或活动线索。
- 目标完成时间 5–10 分钟。
- 月度外部 API 和模型预算目标为人民币 200–500 元。

预算达到阈值时暂停新增调用，并请求用户确认。

### 14.2 可靠性

- 单个非核心数据源失败时继续任务，并标记降级。
- 专利主线完全不可用时将运行标记为“部分完成”。
- SSE 断线后根据事件序号恢复。
- 所有长任务支持超时、取消和有限重试。
- 所有写入操作具备幂等键。

### 14.3 安全

- 密钥只通过环境变量或本地密钥管理提供。
- 上传文件限制类型和大小，文件名不直接作为存储路径。
- 外部 URL 采集防范 SSRF，仅允许 HTTP/HTTPS 并限制私网地址。
- HTML 清洗后再展示，避免脚本注入。
- 日志中不记录密钥、完整提示词私密内容或敏感上传资料。
- 用户删除资料时同步删除其向量和派生数据。

### 14.4 合规与来源治理

- 每个连接器维护许可和采集策略说明。
- 保存来源 URL、时间、hash、内容类型和允许的展示范围。
- 新闻正文默认不长期保存。
- 不绕过访问控制，不伪造 User-Agent 身份。
- 对允许再分发和仅允许本地使用的数据进行分级。
- 导出报告只包含必要引用，不打包受限制的完整原文。

### 14.5 可维护性

- 前后端共享事件和 DTO 契约，接口变更可检测。
- 每个连接器有独立契约测试和录制样本。
- Agent 节点保持小职责、显式输入输出和独立评测。
- 数据 schema、提示词、工作流和数据集均有版本号。

## 15. 状态与失败模型

研究运行主要状态：

```text
draft
  → planning
  → awaiting_plan_approval
  → collecting
  → resolving_entities
  → analyzing_evidence
  → awaiting_report_approval
  → generating_report
  → completed
```

任一执行状态还可进入：

- `partially_completed`：部分来源失败但已有可用结果。
- `failed`：无法继续且没有足够结果。
- `cancelled`：用户取消。
- `paused_budget`：达到费用或调用预算，等待确认。

失败记录必须包含错误分类、可否重试、失败节点、影响范围和已保留产物。

## 16. 评测与验收

### 16.1 固定评测集

建立 10–20 个固定研究案例，覆盖：

- AI 芯片和工业视觉两个种子领域。
- 同名公司、曾用名、子公司和 IP 控股主体。
- 专利族重复、字段缺失和法律状态冲突。
- 新闻实体误判、重复报道和来源冲突。
- 数据源超时、限流和部分不可用。
- 中文问题、英文来源和中文报告。

### 16.2 初始质量指标

| 指标                      | MVP 目标                   |
| ------------------------- | -------------------------- |
| 结构化输出成功率          | ≥ 95%                      |
| 报告关键事实引用覆盖率    | ≥ 90%                      |
| 引用与事实一致率          | ≥ 85%                      |
| 已知公司召回率            | 达到 Data Spike 建立的基线 |
| 无证据推断标记率          | 100%                       |
| 任务刷新后恢复            | 关键场景全部通过           |
| Fixture/Replay 演示成功率 | 100%                       |
| 单次默认运行              | 不超过配置的时间与费用上限 |

指标是起始目标。Data Spike 后先记录真实基线，再调整不现实或区分度不足的阈值。

### 16.3 MVP 验收场景

完整演示至少通过以下场景：

1. 用户创建“工业视觉边缘推理”研究项目。
2. Planner 生成可编辑的方向、CPC 和关键词策略。
3. 用户确认后启动 Catalog 或 Fixture 研究。
4. 系统展示专利、公司和证据工具调用进度。
5. 系统发现候选企业并完成至少一批实体匹配。
6. 用户查看并处理一个待确认实体。
7. 系统生成最多 10 家候选企业长名单和排序理由。
8. 用户选择一家企业生成带引用报告。
9. 报告显示至少一个冲突、缺失或推断标记。
10. 用户刷新页面后任务和报告仍可恢复。
11. 用户导出 Markdown 报告。
12. 同一场景可以用 Replay 模式稳定重放。

## 19. 风险与应对

| 风险                        | 影响                 | 应对                                                  |
| --------------------------- | -------------------- | ----------------------------------------------------- |
| 数据源限流或接口迁移        | Live 任务失败        | 适配器隔离、健康检查、Fixture/Replay、缓存和软降级    |
| 数据许可不明确              | 无法保存或公开数据   | 来源策略、最小引用、许可分级和本地数据包              |
| 中国公司数据不足            | 报告字段不完整       | 明示覆盖边界、用户上传、后续合法商业 API              |
| 专利权人映射错误            | 候选企业和结论失真   | 强标识优先、中低置信度人工审核、保留映射证据          |
| 头部大公司淹没结果          | 难发现中小企业       | 受让人集中度评测、分层排序、新闻/论文补充发现         |
| LLM 幻觉                    | 生成错误事实         | 证据优先、引用校验、推断标记、禁止补写缺失数据        |
| 多服务复杂度过高            | 延误 MVP             | Python 单服务模块化、单用户、本地优先、延后拆分       |
| 数据工程吞噬 Agent 学习时间 | 主流程无法完成       | 以 Data Gate 限制前置规模，通过后让主库扩充与产品并行 |
| 成本和延迟失控              | 无法日常使用         | 默认预算、低成本模型、缓存、批处理和人工确认          |
| clean-room 边界模糊         | 个人项目知识产权风险 | 使用新名称和新实现，不复制公司资产或私有信息          |

## 23. 最终范围基线

在开始开发前，以下决策视为已确认：

- 个人独立学习与作品演示优先。
- 使用 React + NestJS + Python 完成重写。
- NestJS 负责产品服务端；Python Intelligence 只负责 Agent 和研究工作流。
- 离线 Data Foundation 负责采集、解析、数据集构建和 Catalog 发布，与在线 Python 服务物理分离。
- 使用可控状态图和专业 Agent，不使用无限自主 Agent 群聊。
- 最小垂直领域公司—专利数据库和 Data Gate 已完成；下一步是只读产品查询层。
- 全量导入 GLEIF 和 SEC 等许可清晰的官方公司身份文件，建立公司身份参考库。
- 垂直主库持续增量扩充，研究工作集和 Fixture/Replay 分层管理；不镜像全球专利全文和新闻正文。
- 首批领域为 AI 芯片/边缘推理加速和工业视觉/AI 质检。
- 关键事实必须有证据，模型推断必须显式标记。
- MVP 单用户、本地优先，并在 8–10 周内形成可稳定演示的闭环。
